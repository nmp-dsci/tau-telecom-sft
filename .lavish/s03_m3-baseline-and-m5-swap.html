Five things the untrained 4B does, and what dataset v1 shows it instead

  • No MMS task passed on either split (0 of 17 test, 0 of 32 train). MMS tasks stack the most root issues. They're also v1's largest symptom: 212 of its 518 conversations.
  • Its passes are service issues: all 8 on train, and 3 of the 6 on test; the other 3 are mobile data. Every one of them is also a pass for Claude v2 on test except airplane_mode_on · bad_network_preference (Hard), which only the 4B passed.
  • It calls the customer's phone tools itself. 144 of 347 test calls and 244 of 617 train calls were tools like check_network_status that belong to the phone, so each comes back "not found". v1's 518 conversations contain none: the agent always asks the customer.
  • Its conversations run long: 34 agent turns on average on test and 37 on train, against Claude v2's 23–24 and v1's median of 14 (max 32). Four outgrew the 32K context (vLLM refused their next turn) and two ran to tau2's 200-step limit.
  • Some tool calls come back as text: 10 replies on test and 86 on train wrote the call into the message instead of tool_calls, so tau2 treated them as words to the customer. v1's targets are all structured calls, in the same hermes format vLLM parses.

02 · architecture

Only the agent's replies come from Modal, and everything else runs on your Mac

The picture as built and run today. Accent outlines are M3's new pieces; the highlighted path is one agent turn. Nothing on Modal reads or writes MLflow, and nothing on the Mac changed except the proxy and the scoring command.

On Modal: one thing

A vLLM server with the base model's weights, answering chat completions. It holds no conversation state between requests: each request carries the whole history, and vLLM's prefix cache makes the repeated part cheap. It never sees the customer, the tools' results before tau2-loop sends them, or the grade.

On the Mac: everything else

tau2-loop runs the conversation: it asks the student for the agent's turn, runs the tool call the student chose against tau2's telecom database, asks Haiku for the customer's turn (which runs the phone's tools), and grades the end state. So the GPU is busy only while the agent writes; the customer's turns are the slow part.

Between them: the proxy

The one piece of Mac code that knows the model is remote. It adds the token, waits out a cold start, and logs every request's hashes. score-pull checks those hashes against the dataset card, so R0 and R1 provably saw the same prompt and tools as the training data.

03 · one agent turn

A turn is one HTTPS request with the whole conversation in it, and a tool call comes back as JSON

The opening of a real R0 conversation on the test split, one that passed: [mobile_data_issue] airplane_mode_on · data_mode_off, persona None. tau2-loop drives; the student only chooses the next message or tool call. Its fourth call is the mistake behind 41% of R0's tool calls on the test split.

Two consequences. First, the student has no memory on Modal: a preempted container loses nothing but its cache, and the proxy's retry carries the conversation on. Second, every request repeats the ~7K-token prefix, so vLLM's prefix cache matters more than raw speed: it served 99% of prompt tokens from cache in these runs.

04 · the agent

s3 is tau2's stock agent with the 4B as its model, so the score is the model's alone

A tau2-loop "version" is a folder: an agent.yaml and the surfaces it loads. Claude's v-versions carry the loop's edits to the prompt; the students' s-versions carry none. s3 lives in the worktree ../tau2-loop-student on branch feat/open-student (commit b2a84c6), never in tau2-loop's main checkout.

What the 4B is given

  • The system prompt: tau2's stock 9 lines with the telecom policy in {policy}. Its sha256 b76554cc… equals the one dataset v1 was rendered with.
  • 13 agent tools in the API's tools field (tool_mode: native): get_customer_by_phone, get_details_by_id, suspend_line, refuel_data, transfer_to_human_agents, …; sha256 66b1aa33…, again the dataset's.
  • Sampling: temperature 0.7, top_p 0.8, top_k 20, Qwen's recommended settings for the Instruct model, and the ones M4 trains under.
  • Up to 200 steps, parallel tool calls allowed.

What it's compared with

  • Claude v2 (R5): Haiku 5.5 at high effort as the agent, with the loop's edited prompt and JSON tool mode. Same split, same customer, one trial.
  • R1 at M5: s4, the same folder with one line changed, model: student-qwen3-4b-sft-a (§07).
  • What never changes between R0 and R1: the prompt bytes, the tools, the sampling, the customer, the rules, the split, one trial per task, vLLM's version and flags, the GPU. Only the weights.

src/tau_telecom_sft/serve/remote.py new

On the Mac, MLX wrote a serve.json beside the weights. On Modal there's no file to read, so describe() builds the same record from modal_app's constants and the tokenizer at the pinned revision. score-pull writes it into the eval run, and at M5 it carries the adapter's sha256 from M4's run.json.

Why the proxy waits before it listens: tau2-loop's first request would otherwise sit through a five-minute cold start. A 401 or 403 stops at once (a bad token isn't worth retrying), and a name the deployed Student doesn't serve stops with "redeploy".

07 · M5: swapping the base for the tuned model

At M5 the same container serves both models, and the agent version picks one by name

M4 trains a LoRA adapter: about 33 million extra weights (rank 16 on every linear layer, 0.8% of the 4B) that sit beside the base weights rather than replacing them. vLLM loads the base once and applies the adapter only to requests that ask for its name. So R1 isn't a different server, a different prompt or a different proxy. It's a different model string in the request.

tau2-loop: s3 → s4 agent.yaml, proposed

Why an adapter by name, and not merged weights? Merging the adapter into a new 8 GB checkpoint would also work, but it would be a second model to download and serve, and R0 and R1 would come from different servers. Served by name, both runs share the base's exact bytes, the container and the prefix cache, so the only thing that can differ is the adapter. vLLM's LoRA path costs a little speed per token; the measured conversation at M5 will show how much.
