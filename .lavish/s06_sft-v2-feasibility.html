SFT v2: train on what R1 got wrong, in the harness it's scored in

You can't train on Claude v2's conversations: both seats in them are Claude. You can get the same kind of conversation by putting an open teacher in the agent's seat of the scoring harness. The new rows then match scoring byte for byte on the agent's side, and the customer runs scoring's prompt and rules. You pick the customer's model. Then M4's adapter keeps training on v1.1 plus the new rows. Every piece is feasible. The work is code changes in two places. The tau2-loop worktree needs a teacher version, a customer pass-through and a fork option. This repo needs init_adapter, loss on part of a row, and the build.

01 · answers

Your four questions

Can the conversations built with Claude be fine-tuned on?

No, not as training rows.

Claude v2's runs aren't only Claude in the agent's seat. The agent is Haiku 5.5 at high effort, running a prompt with a checklist that Sonnet wrote. The customer is Haiku 5.5 as well. Training on that text is what rule 2 forbids ("tau2-loop's Claude runs may be read for comparison, never trained on"). Rule 2 cites Anthropic's Consumer Terms, which bar using outputs to build a competing model. Putting no loss on those turns doesn't change that.

What they're good for, and what this page uses them for: choosing the patch set (§04), showing how long a pass takes against this customer (a median of 27 agent turns on the 19 tasks), and listing the situations a passing agent gets through (§03).

Do they look exactly like the conversations we build from and score on?

Partly. The customer and the file are the same; the agent isn't.

The customer is the same as in R1's scoring runs, and so is the file: tau2's Results, which our loader already reads. The agent side is different. Claude v2 gets the 37-line checklist, a clock note and a JSON tool contract. Each turn, it sees the whole conversation as text blocks in one Claude Agent SDK query. The student is trained on, and scored with, tau2's stock prompt and native OpenAI tool calls. The board rows we trained on match the student's agent side but not its customer. §02 has the full comparison.

Can the training conversations look the same as scoring?

Yes, by running them in the scoring harness.

Add a teacher version next to s4 in the tau2-loop worktree. It keeps s4's agent.yaml (the same LoopAgent, stock prompt bytes, the 13 tools, native calls, 200 messages and 10 errors) and swaps only the model, which is served through our recording proxy. The proxy already logs a hash of every prompt it serves, so the prompt-bytes check proves the match. The runs write the same tau2_results.json a scoring run writes.

The one seat left to choose is the customer. Its prompt and tau2_loop/2 rules can stay exactly as they are in scoring. Its model can't be Haiku (decision 1).

Can v2 load v1's adapter and keep training?

Yes, with one change to the trainer.

M4's adapter is already on the Modal runs Volume that the trainer mounts (/repo/runs/20261020T204721Z_train_sft-a-4b/adapter, sha256 8956c198…). Today every run starts a fresh LoRA. The change is an init_adapter key that loads M4's adapter as trainable and checks its sha256. The new adapter keeps M4's r16 all-linear shape, so vLLM serves it beside M4's with one more --lora-modules entry. §06 has the details.

A correction to s05. s05 said the customer that refuses checks and disputes charges is the "tau2_loop/2" customer. The rules aren't the cause. tau2-loop's customer is tau2's stock customer prompt plus three rules: a stop sent with words is held, then sent alone; both sides get a fixed clock; and a reply that speaks as an AI or writes a tool call as text is sent back. Nothing in them tells the customer to refuse or dispute. So the change from v1.1 to scoring is the model (gpt-5.2 low to Haiku 5.5 high), plus R1's own repeats provoking the refusals. That's why decision 1 is about the model and keeps the prompt and rules as they are.

03 · what the errors add

Seven observations that s05 didn't have

They come from the 74 training tasks: R1 against Claude v2 task by task, and against what v1.1 holds. The test runs are read for checks only. Nothing on this page that selects data comes from a test task.

1 · The tasks aren't missing; the situations are

changes the fix

19 of 19 patch tasks already have 4–8 v1.1 rows

Every task that R1 fails and Claude v2 passes has a median of 7 v1.1 rows. More of the same board conversations won't fix them. What R1 hasn't seen is the conversation going the way it goes against this customer.

2 · The customer writes differently

input shift

92% → 0% of customer messages use markdown bold

gpt-5.2 at low effort writes like a report. It uses bold, names the phone function it ran (can_send_mms()) in 14% of messages, and has a median of 36 words. Haiku writes plain prose of about 60 words and never names a function. R1 trained on 4,809 customer messages, and none look like the ones it's scored against.

3 · A pass takes about twice as long

length shift

27 agent turns for Claude v2 to pass the patch tasks; v1.1's median is 14

Claude v2 passes the 19 tasks in a median of 27 agent turns and at most 42. v1.1's rows have a median of 14, a 90th percentile of 21 and a maximum of 32. Only 2 of 518 rows go past turn 29.

4 · What R1 repeats when it loops

the loop's content

34 of 41 failures loop, starting at a median of turn 27

Counted per conversation, after the loop starts: 25 re-send a message, usually asking for a check the customer already ran. 23 re-read the line (get_details_by_id) and 15 re-read data usage (get_data_usage). R1 goes back to reading the account instead of moving on to the next cause.

5 · Refusals are what R1 never saw

the missing situation

23 of 41 R1 failures have a refusal; v1.1 has 2 of 518

"I'm not going to run check_apn_settings again. That's the fifth time, and it has returned the same APN name and MMSC URL every time…"customer, R1 training run

Disputes show the same gap: 5 of 41 against 0 of 518. Claude v2's passes meet refusals too (7 of 45), so a passing agent has to get past them, not only avoid them.

6 · Claude v2 isn't a ceiling on every persona

where to aim

Hard persona: Claude v2 6/36, R1 14/36

Claude v2 is far ahead on Easy (32/38 against 19/38) and None (31/40 against 17/40), but behind R1 on Hard (train and test together). So where R1 loses to Claude is mostly Easy and None: 16 of the 19 patch tasks.

7 · Long, many-issue MMS tasks are the hard core

scope

8–9 root issues: R1 0/10, Claude v2 4/10

MMS is 10 of the 19 patch tasks and 16 of the 22 that both fail. A task with many root issues needs the agent to keep going after each fix that "didn't work". Neither customer makes that rare: both say "still not working" often. What's rare in v1.1 is going past turn 30.

Not new: frustration and "what next?"

already covered

gpt-5.2 also says "still not working" (267 of 518 rows), gets frustrated (266) and asks what to try next (391). R1 has already seen those, so they don't need patching.

The rules for the patch set

  • Training tasks only. Patch tasks come from R1's and Claude v2's training runs. The leak check runs on v2 as it did on v1.1, so no test task or twin gets in.
  • R1's misses on test only measure the result. They don't choose any data. Otherwise R4's test score would be in-sample.
  • Tier 1 by symptom: 10 MMS, 6 mobile data, 3 service. Tier 2: 16 MMS, 2 mobile data, 4 service.
  • Endings in tier 1: 15 hit the 200-message limit, 4 ended with the customer stopping. None ended on too many errors.
  • The other 33 tasks stay in through v1.1's rows, so what already works keeps being trained.

05 · generate, build, train, score

How v2 rows are made so they look like scoring

There are two kinds of row, both written by the scoring harness. Fresh rows show the teacher solving a patch task against this customer from the first turn. Recovery rows start from R1's own conversation at the turn where it began to loop, and the teacher carries on from there. Only the teacher's turns get loss.

Fresh rows: small changes, all in the worktree

  • A teacher version telecom/t1 copies s4's agent.yaml and changes only the model. Its STUDENTS entry is one line in llm/core.py, which is where tau2-loop names models.
  • The route goes through our recording proxy, which sends it on to OpenRouter (serve/proxy.py already takes headers= and rewrite_model=). tau2-loop keeps its "no-key" student route, and every served prompt is hashed for the prompt-bytes check.
  • The customer model gets passed through. runner.py:212-213 and :279 force every customer through claude-sdk/, so a non-Claude name needs a pass-through there. The customer's prompt and the tau2_loop/2 rules stay as they are. tau2-loop's billing rule ("the customer stays on the subscription") gets a recorded exception, like the one students already have for the agent.
  • Run: uv run tau2loop eval --domain telecom --agent t1 --task '<id>' … --trials 4, calling the CLI directly because the Makefile doesn't quote telecom's [ ] |.

Recovery rows: tau2 supports the replay; tau2-loop needs a way in

  • tau2 can start from a history. A task's initial_state.message_history is replayed into the environment, and the agent and customer states start from it (orchestrator.py:497-560). tau2-loop's customer inherits that from tau2's UserSimulator.
  • What tau2-loop lacks is a way to pass in a forked task: a copy of the training task whose history is R1's conversation up to the loop. That's a --fork option or a task file in the worktree. It's the largest change on this page.
  • The prefix needs a non-Claude customer too. The 34 loop states in today's R1 run were reached against Haiku, so their customer turns are Claude's text. R1 first replays the 41 failed tasks with the decision-1 customer (about $1–3 on the L4), and the forks come from those runs.
  • The rows need one trainer change: R1's prefix is the prompt and the teacher's turns are the completion (§06).
06 · continuing M4's adapter

v2 keeps training v1's adapter: what exists and what changes

What already works

  • The adapter is where the trainer can read it. The trainer mounts the runs Volume at /repo/runs, and M4's adapter is at 20261020T204721Z_train_sft-a-4b/adapter. sync.py keeps a sha256-checked copy on the Mac.
  • The data path is unchanged. make modal-data VERSION=v2 runs the leak check and uploads train.jsonl and stats.json. The job refuses a file whose sha256 doesn't match.
  • Serving. Add one ADAPTERS entry and the Student serves both. Set --max-loras 2, since it's unset today and vLLM's default is 1.
  • Time limits. Each attempt can run 8 h. M4 took 6.1 h for 3 epochs of v1.1, and 1 epoch of v2 is about 3 h.

The three trainer changes

  • init_adapter: today every run builds a fresh LoRA through peft_config (sft.py:252-259). The new key loads PeftModel.from_pretrained(model, path, is_trainable=True) and checks the adapter's sha256 against M4's run.json. It passes that model to SFTTrainer without a peft_config and records the parent in run.json and MLflow.
  • Loss on part of a row: today every assistant turn is trained, and mask.py:60-75 rejects a row that isn't. TRL 1.16 has prompt/completion rows whose loss covers only the completion's assistant turns (sft_trainer.py:1322-1369). Every v2 row takes that shape: v1.1 and fresh rows are the system prompt as the prompt and the rest as the completion, and recovery rows put R1's prefix in the prompt. The mask check then compares against the completion.
  • Build: a pinned source for the teacher runs, and a CLI build that takes more than the board files (cli.py:147-164). Two filters change. F6 (too long) uses each source's own median, so long passes against Haiku-style customers aren't dropped against the board's median of 14. F5 (agent tool error) ignores errors inside R1's prefix.

Risks, and how each is checked

  • Forgetting what works. All 518 v1.1 rows are replayed, and R4 is compared with R1 on the 33 tasks R1 passes. "Broke" stays at 2 or fewer, as R1's was.
  • Longer rows on the L4. New rows reach about 16–22K tokens. M4 peaked at 16.04 GB on 16.9K tokens, out of 24 GB. The measured step runs the 3 longest v2 rows first (LONGEST=3).
  • Over-fitting to 41 tasks. Rows are capped by F9 (3 per task and tool path), there are 4 teacher trials per task, and the score is on test, which no patch row comes from.
  • Optimizer state. It doesn't carry over and doesn't need to. The data and schedule are new, so a fresh warmup at a lower rate is standard.
  • A clean results table. R4 is "M4 + v2", so it names its parent. If you'd rather have one recipe from scratch, retrain on v2 for 3 epochs: about 8 h, right at one attempt's limit, so it may need the checkpoint resume.
