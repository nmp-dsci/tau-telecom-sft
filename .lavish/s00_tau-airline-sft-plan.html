tau-telecom-sft: shadow the TMLS talk and teach an open model tau2 telecom

This is the plan for a repo you'll create. It repeats Kai Wei Tan's TMLS talk on the same domain, telecom, using your own tau2-loop split of the same 114 tasks, so the student and your Claude agent face the same 40 test tasks. It covers where the training conversations come from, how they're filtered and formatted, how the student is trained, served and scored, and how you track progress. It was first written for airline and was pointed at telecom on 16 Oct. Nothing in it has been built, downloaded, trained or run.

The plan in six points

  1. Use your split: tau2-loop's telecom split v3, 74 training and 40 test tasks, the one your Claude v2 agent ran on (24/40 on test). Train on all 74, the same set Claude v2 used, and play the 40 test tasks once per model.
  2. Data: the board's conversations now, the talk's teacher only if needed.
    • Now, free: taubench.com publishes GLM-5's and Qwen3.5-397B's telecom conversations, 4 trials of every task: 592 on the training tasks. Sierra ran both in tau2's standard tool-calling loop (§4).
    • Only if needed: running the talk's teacher, GLM-5.1, about 12 times per training task (about 822 conversations, $40 to $140) waits until a result shows the board data is what's holding the student back (M7).
  3. A pass alone isn't enough, which was the talk's main lesson. Ten filters drop passes that called a missing tool, hit a tool error or ran long. Every drop is counted.
  4. Train in two steps:
    • Qwen3-4B on one EC2 L4 first, which is cheap and proves the pipeline.
    • Then the talk's own Qwen3-30B-A3B on one rented 80 GB GPU (an A100 on RunPod or Modal), as the true shadow.
    Both use LoRA in TRL, with the loss on the agent's turns only.
  5. Serve and score: vLLM serves the tuned model on the GPU it trained on. tau2-loop on your Mac plays the 40 test tasks 4 times each, with the same Haiku 5.5 customer your v2 agent faced. Report pass^3 as the talk did, plus pass^1 to pass^4 and a paired test against the untrained model.
  6. Track progress in the repo:
    • a milestone checklist in ai_specs/ and a status table in the README;
    • a dataset card for each data build;
    • MLflow experiments tau-telecom-sft/data, /train and /eval.
1 · Goal and starting point

Repeat the talk's telecom result with your own pipeline, then show where yours differs

The talk took Qwen3 30B from passing none of the telecom test tasks three times running to 75% after SFT and 77.5% after RL, beating GPT-4.1 mini. This repo repeats the SFT half with the same kind of teacher data on your own split, and measures it with your own harness. RL stays out of scope, as before.

Success criteria, fixed before training (M4)

What counts as a result

  • Floor: the tuned student beats the untrained one on the 40 test tasks. That means a one-sided sign test p < 0.05 on the tasks that changed, which is tau2-loop's own gate.
  • Target, 4B: pass^3 of 50% or more on test.
  • Target, 30B shadow: pass^3 of 70% or more, against the talk's 75%.
  • Head-to-head: your Claude v2 passed 24 of these 40 test tasks (60%) in one trial. R5 replays it with 4 trials, so it can be compared on pass^3.
  • Always: report counts as well as percentages. With 40 tasks, each one is worth 2.5 points.
Where you start

What already exists

  • tau2 telecom (tau2-loop's pin 2174a60):
    • 114 base tasks. tau2 ships its own 74/40 split; this plan uses yours (below);
    • a 3,715-word policy and 13 agent tools;
    • 30 tools on the customer's phone, which the customer runs, not the agent.
    A task is graded on the phone's final state: for example, mobile data on and the speed test excellent.
  • tau2-loop's telecom split v3 (16 Oct): a fresh seed-300 draw of the 114 tasks, 74 train and 40 test, stratified by symptom and persona.
  • Your Claude telecom v2 (Haiku 5.5 at high effort, the v1 prompt) on split v3: 45/74 on train and 24/40 on test, one trial each, with a Haiku 5.5 customer at high effort and rules tau2_loop/2.
  • The board's telecom scores (pass^1, all 114 tasks):
    • GLM-5 86.8% and Qwen3.5-397B 97.8%;
    • GPT-4.1 mini 48.9% (pass^3 31.2%), from an older tau2 version with a GPT-4.1 customer.

How the talk collected its 822 conversations

What the talk says

Yes: the teacher ran many attempts on the training tasks only

  • Teacher: GLM 5.1 played tau2's 74 telecom training tasks, against tau2's customer simulator.
  • Coverage: it solved 68 of the 74.
  • Volume: the speaker then "got more rollouts", 822 in all. That's about 11 per task, or 12 per solved task.
  • Logging: each rollout is one multi-turn conversation, logged as a trace in Weights & Biases. A customer prompt sets the scenario and a persona from easy to hard.
  • Filtering: the speaker kept 669 clean ones, and also mentions "760 raw trajectories", which is probably the passing ones before the quality filter.
What the talk doesn't say

Choices you'll make yourself

  • Attempts per task: how many, and whether only the solved tasks were re-run.
  • The customer model: which model played the customer, and at what temperature.
  • The generated pool: whether any of tau2's 2,285 generated tasks were used. The talk only mentions 74.
  • Checkpoint choice: how the SFT checkpoint was picked. This plan trains on all 74 tasks, so it fixes the epoch count in advance and keeps the final checkpoint.
  • The test set: which tasks the test scores came from. Every score the talk gives (0, 37.5, 75, 77.5%) is a multiple of 2.5%, which is 1 task in 40, so almost certainly tau2's 40 test tasks.

The talk's main lesson applies here unchanged. The speaker first trained on every passing run, and RL on top was unstable. On inspection, many passing runs had called tools that don't exist or had passed by luck. Filtering for clean runs, not just passing ones, is what made SFT work.

SFT and RL are two different steps

SFT first, then RL, is the usual order. SFT teaches the format and the procedure cheaply, and RL then sharpens a model that already mostly works. RL from scratch on a model that passes nothing gets almost no reward to learn from.

Why the talk's lift was possible: telecom's test tasks recombine what the training tasks teach. Each task is a symptom plus a set of root issues plus a customer persona.
  • The 40 test tasks are new combinations: none repeats a training task's exact set of root issues.
  • But every root issue in them also appears in the 74 training tasks: 3 symptoms and 19 root issues in train.
So a result here shows the model handles known faults in new combinations, not faults it has never seen. State it that way.
2 · The pipeline

Six steps, from conversations to a score on held-out tasks

Data work runs on your Mac. Training and serving run in one container on a rented GPU. Scoring runs in tau2-loop on the Mac, which reaches the GPU through a port forward. Every step writes a record that progress tracking reads (§10).

What carries between steps:
  • a dataset version (JSONL and its card), stored under its content hash;
  • an adapter, with the image tag and data hash beside it;
  • an endpoint the scorer calls;
  • a tau2-loop run folder that tau-telecom-sft records.
The two green boxes are where this plan differs most from a naive one: the filter, and scoring with the same protocol for every model.

How the S3 estimate was made

Telecom conversations are longer than airline's

  • Token counts: I took them from tau2-loop's 60 telecom conversations. The median is 14 agent turns and 140K prompt tokens per conversation; p90 is 241K. The customer also makes a median of 9 phone tool calls of its own, so a conversation takes about 5 minutes.
  • Price per conversation: at GLM-5.1's prices, that is about $0.03 if the cache holds the shared prefix and $0.14 if nothing is cached. The open-model customer adds a few cents.
  • Caveats: Haiku's tokenizer and tau2-loop's prompt differ from the teacher's, so treat this as an order of magnitude. If M7 runs, it measures one real conversation before any batch.
Before you rely on the board files

Five things M1 checks after downloading

  • The customer's phone calls. The files hold the customer's tool calls and results too. The agent never sees those, so they come out (§6).
  • Reasoning text. Both models ran with thinking on. For a non-thinking student, only replies and tool calls are kept. Check whether the files hold reasoning at all: tau2 keeps the provider's raw response in each message's raw_data, which is the only place it could be.
  • The system prompt. If the files don't carry it, rebuild it from tau2's SYSTEM_PROMPT and the telecom policy at the pin. The policy is the main policy plus the tech-support manual.
  • Customer turns. These are GPT-5.2 output. They go in as context, with no loss on them. Whether that's fine under OpenAI's terms is your call. S3 with an open customer would avoid the question, if it's ever run.
  • License. tau2-bench is MIT. I found no separate license on the published conversations. Note that in the dataset card.

How the board ran these models: a native tool-calling loop, not a text ReAct prompt

Sierra ran both models in tau2's standard agent, with the stock prompt unmodified (their submission files say "Standard tau-bench scaffold"). Each model ran at temperature 1.0, top_p 0.95, seed 300. Qwen3.5 was self-hosted on vLLM. The loop has three players, and the agent is the only one being tested.

Each turn: tau2 sends the agent the whole conversation so far, with the 13 tool schemas in the API's tools field and tool_choice: auto. If the answer is tool calls, tau2 runs them and calls the agent again with the results. If it's text, the customer gets it. That repeats until the customer sends its stop token, or a cap on steps or tool errors ends it.

Short answer: yes, it's a ReAct-style loop of think, act, observe, but with native tool calling. Nobody writes a "Thought: / Action: / Observation:" prompt or parses tool calls out of text. The model's own API returns structured tool calls, and its thinking (when on) happens inside the model.

The filters never look at the customer's wording, so customer style isn't filtered. F1 to F10 are pure functions in build/filters.py, tested on small fixture conversations that need no network or GPU.

What happens to the conversations that fail

SFT trains only on clean passes, so the model never sees a failed conversation. SFT copies every agent token it's shown, so a failed conversation would teach its mistakes as readily as its good turns. Nothing in SFT learns "don't do this".

The failures are still used, in four ways:

  • 1. They're counted. The dataset card reports every drop by rule. Any task where the teacher fails every time gets no training data, and the card shows it. The talk's teacher failed 6 of 74.
  • 2. Recovered errors can be kept, in a later dataset version. A pass that hit a tool error and then fixed it stays in, with the loss switched off on the bad call only. The student learns the recovery, not the error.
  • 3. The part before the first mistake can be kept, also an option. Train on the turns before the first wrong step, with the rest masked. This is riskier: a correct-looking early step can still start a bad diagnosis.
  • 4. The stage after SFT learns from them directly. Preference training (DPO) pairs a passing and a failing conversation on the same task. RL, like the talk's GRPO, pushes down runs that score below the group average. It's out of scope for this repo and is noted for the follow-on plan.
6 · Training format

One conversation per line, as the agent saw it, with loss on the agent's turns only

Conversion rules

From tau2 messages to chat format

  • The agent's view only. A telecom conversation has two tool users: the agent and the customer's phone. tau2 shows the agent only its own calls and results and the customer's text replies (is_valid_agent_history_message in tau2's base_agent.py). The converter applies that same function, so the customer's phone calls and results never appear.
  • System prompt: tau2's stock agent prompt (SYSTEM_PROMPT, with the telecom policy and tech-support manual) byte for byte at the pin. The student is scored with exactly the same bytes (§8).
  • Tools: the 13 agent tool schemas from tau2 at the pin, passed as tools so the student's own chat template formats them.
  • Turns: each agent turn becomes an assistant message, either text or tool calls. Customer turns become user; agent tool results become tool.
  • Dropped: reasoning text, cost and usage fields, timestamps.
  • Loss: on assistant turns only, every one in one pass. Customer turns and tool results are context.
  • Metadata: the meta object goes in the card and the provenance logs, never into the model's input.

The 13 agent tools. The six outlined ones change the customer's account. Fixes on the phone itself (airplane mode, APN, app permissions) are the customer's tools, which the agent can only ask for in words.

Dataset versions

Versions are append-only, and each has a card

  • The versions:
    • v1: S1 and S2 (the board), filters F1 to F10. Every result up to M6 uses it;
    • v2, only if M7 runs: v1 plus S3, the GLM-5.1 conversations;
    • later, optional: masked recoveries (§5) or pool tasks (D6), each as a new version.
    A version never changes; a new rule means a new version.
  • Card: data/sft/vN/card.md is committed. It holds:
    • the sources with their sha256 hashes and download dates;
    • the filter table, and counts by task, symptom, root issue and source (M7's trigger reads the root-issue counts);
    • the length distribution;
    • the hash of train.jsonl.
  • Storage: the JSONL files go to S3 under their content hash. The Mac keeps a copy in data/sft/vN/, which git ignores.
  • Expected scale: v1 should be about 430 to 520 conversations, at roughly 10K to 20K tokens each.

Does a conversation appear several times? No: one conversation is one row, trained at every agent turn

  • Each conversation is in the file once. In one pass the model learns every agent decision in it: the greeting, each tool call, each instruction to the customer and the close. Each decision sees the true conversation before it.
  • What appears many times is the task, not the conversation. The teacher plays each training task about 8 to 12 times, so the file holds several different conversations per task. F9 caps near-identical ones at 3.
  • The alternative is one row per agent turn. Each row ends at a different agent turn and only that turn is trained, so the same conversation does appear many times, cut at different points. It teaches the same thing, but repeats the history each time: about 14 rows and roughly 100K+ tokens instead of one 15K row. Use it only if the trainer can train just the last message, or for a thinking student whose template drops earlier reasoning.
  • Grading isn't per turn. tau2 grades the conversation as a whole, from the phone's final state, which is why filters keep or drop whole conversations.

How one input trains every decision: the output is a guess at every token

Short answer: in training, the model doesn't produce one answer at the end. It reads the whole conversation once and, at every position, outputs a guess at the next token. The target at each position is simply the token that actually comes next. Only the guesses for the agent's tokens are scored. Because each position can only look backwards, the guess for agent turn 5 uses only what happened before turn 5. So one row gives the same lesson as cutting the conversation at each agent turn, without repeating it.

  1. Input. The row, rendered by the chat template, is one sequence of about 15K tokens: system prompt and tools, then every turn in order (the worked example shows it in full).
  2. One forward pass. At every one of those positions, the model outputs a probability for each of its 151,936 vocabulary tokens being next. That table of guesses is the training "output". Nothing is generated.
  3. Targets. The targets are the input shifted left by one: the target at position t is the real token at t + 1. They come free from the conversation itself; nobody writes them.
  4. Mask. If the target belongs to the agent's turn, it counts. If it belongs to the system prompt, the customer or a tool result, its label is −100 and it's ignored.
  5. Looking backwards only. Attention is causal: position t can read positions 1 to t, never later ones. The guess at each agent token is made from exactly the history the agent had at that moment.
  6. Loss and update. The loss is the average of −log p(target) over the agent's tokens. One backward pass updates the LoRA weights for all the agent's decisions in the conversation at once.

Reading it: each arrow takes a token one step left, to become the target of the position before it. Position 3 is the assistant header: from everything before it, the model must guess "What's", the first token of its reply. Position 8 is the header before the tool call: there it must guess ‹call›, which is the decision to call a tool. Tokens are simplified here; real ones are word pieces.

Why one row equals many cuts

Each position sees only its past

  • Row 8 is highlighted: the moment the agent decides to call a tool. It sees positions 1 to 8, including the customer's number, but not the tool result at 12, which hasn't happened yet.
  • That's the cut you'd have made by hand. A separate row "history up to turn k → turn k" would give each agent token the same view and the same target.
  • So the gradients match. The difference is cost: the shared history is computed once instead of once per agent turn.

How one row trains

One forward pass, seven targets

  • Teacher forcing: the model reads the whole row once. At every trained token it predicts the next token from everything before it, and the input is always the teacher's true history, never the student's own earlier guesses.
  • The loss is the average of −log p(correct token) over the trained tokens only. The update changes only the LoRA adapter's weights; the base model stays frozen.
  • The table above is not seven rows in the file. It's the same single row, seen from each agent turn (as above).
What it doesn't learn

The customer and the tools are never targets

  • Customer turns (GPT-5.2's text in the board files) are context only. The student never learns to talk like the customer.
  • Tool results come from tau2's code. The student learns to read them, not to write them.
  • Whether the conversation passed isn't in the row at all. SFT only sees passing, clean rows, so the filters (§5) are the only place success enters.
7 · Training

LoRA in TRL, in a container: the 4B on one L4, then the talk's Qwen3-30B-A3B on one 80 GB A100

Student, step 1
Qwen/Qwen3-4B-Instruct-2507 (Apache-2.0), a non-thinking model. It's cheap on one L4 and proves the pipeline end to end.
Student, step 2
Qwen/Qwen3-30B-A3B (Apr 2025, Apache-2.0): 30B in total with 3B active per token. It's the talk's model, released before tau2, and the true shadow.
Method
LoRA r 16, alpha 32, on all linear layers (on the 30B, the attention layers and experts). Learning rate 1e-4 with cosine decay, 3 epochs, bf16. All of these are starting points.
Loss
Assistant turns only. TRL patches Qwen3's template to mark them, and M3 checks the mask.
Length
24,576 tokens, with no packing. Gradient checkpointing and Liger kernels on.
Checkpoint
3 epochs, fixed before training, and the final checkpoint is the model. With all 74 tasks trained on, none are left to pick one. Each epoch is still saved, for the record.
Where
  • The 4B: EC2 g6.2xlarge in Sydney, one L4 with 24 GB, at US$1.271 an hour; your quota covers one.
  • The 30B: one 80 GB A100, at $1.79 an hour on RunPod or $2.50 on Modal (both checked 12 Oct), with the same image. Why 24K fits the 4B on 24 GB (estimate, untested)

The output layer is the problem, not the model

  • Model weights in bf16 take about 8 GB. LoRA adds little.
  • The output layer: at 24,576 tokens and Qwen's 151,936-word vocabulary, it produces about 15 GB of scores in fp32. Liger's fused loss never builds that full tensor, which is what makes this fit.
  • The layers' saved inputs with checkpointing take about 4.5 GB at 24K.
  • Speed: an L4 should manage about 1,500 tokens a second here. That is about 50 to 70 minutes an epoch for v1, so a few dollars a run.

How you track progress

The plan

ai_specs/s00_project_plan.md

This milestone list as a checklist. Tick a box when its "done when" holds, and add the date and the run or data hash. The button below copies it as markdown.

The status

README status table

One row per milestone: status, date, evidence. Below it sits the results table from §8, filled in as rows land.

The ledger

Three MLflow experiments

data: one run per dataset build, with drop counts and the card. train: one run per job, with loss curves, config, image tag and data hash. eval: one run per scored model, with pass^k, p and cost.

From the cloud

Object storage, then sync from the Mac

A job in AWS or GCP can't reach MLflow at localhost:5000. It writes metrics.jsonl to the bucket, and make sync-mlflow logs it from the Mac. There's no local store in between.

11 · Risks

Your numbers won't match the talk's exactly; the job is to know why

RiskWhat the plan does
A different customer from the talk's: a Haiku 5.5 customer here, an unknown one there, and GPT-5.2 in the board dataCompare lifts over each model's own base, not raw scores with the talk. State the customer on every row.
Phone calls leak into the agent's view when converting the board filesThe converter uses tau2's own is_valid_agent_history_message, and a test asserts that no customer tool call or result survives.
The test reuses training root issues, so the result could be read as more than it isSay what it shows: known faults in new combinations. If you want a harder claim, a later split could hold out whole root issues.
Generated-pool leakage if D6 adds pool tasksF8 drops any pool task with a test task's exact set of root issues, under any persona, and the leak test checks it.
Long conversations: a median of 15K tokens and a maximum of 26K in tau2-loop's runsA 24K limit, Liger's fused loss and checkpointing; F10 counts what's cut. The 30B on A100s has more room.
Train and serve differ in prompt bytes, the clock note, the tool-call format or samplingM2 runs the untrained 4B through the exact serving path before any training. A test compares the trained system prompt with the served one.
Terms on the board files: their customer turns are GPT-5.2 outputThey are context only, with no loss on them. If S3 is ever run, it uses an open customer. Claude's output is never used.
The 30B is harder to run: about 61 GB of weights, MoE LoRA, and a rented machine outside AWSIt comes last, after the 4B has proved everything. Checkpoint every epoch to the bucket, keep the same image, and stop the machine the moment a run ends.
Noise: a single trial flipped 5 of 25 tasks between two runs of one airline agentUse 4 trials, paired tests by task, and counts beside percentages.
Costs growMeasure one conversation or step before any batch, set budget alarms in AWS and GCP, and stop instances after each run.
