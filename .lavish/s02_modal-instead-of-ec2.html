Modal can run M3 to M5 instead of EC2, with one new file and nothing to build in AWS

You asked whether Modal could serve and fine-tune the 4B instead of EC2, and what s01 would look like with EC2 swapped out. It can. The trainer and the vLLM command don't change, tau2-loop doesn't change, and nothing new is needed in AWS: no Terraform, no Dockerfile, no S3 bucket, no SSH tunnel. One file is new, cloud/modal_app.py, and six get small edits. At list prices M3 to M5 cost about $7–13 on Modal against $9–16 on EC2, and Modal's $30 monthly credit on its free plan probably covers it. What you take on is new: Modal can preempt any GPU container and that can't be turned off, so the trainer has to resume and the proxy has to retry. You also give up some of the enterprise story the plan chose EC2 for.

02 · architecture

The Mac keeps every lane but one, and Modal takes the GPU's place

s01's picture from M3 on. The accent outline marks what's new or changed from the EC2 plan, and the highlighted path is one agent turn being served. Nothing on Modal reads or writes MLflow.

Only the agent is on Modal. The 4B on Modal answers as the agent, the base model for R0 and base plus adapter for R1, and nothing else. On the Mac, tau2-loop does the rest:

  • the customer: Haiku 5.5 at high effort on your Claude subscription, as in every other row of the results table;
  • every tool call: the agent's 13 tools and the customer's phone;
  • the grade.

Each agent turn goes from tau2-loop to the proxy on :8020, then to Modal. A reply or a tool call comes back, and tau2-loop runs that call itself on the Mac. So the GPU works only while the agent writes. The customer's thinking and phone calls happen on your side, which is why the customer, not the L4, limits how many conversations can run at once (M-10).

What changes from the EC2 plan

  • Port forward → HTTPS with a token. The proxy is the only Mac code that knows where the model is.
  • S3 → three storage volumes (Modal calls them Volumes). sync-runs reads from the runs volume instead of a bucket.
  • Dockerfile + Terraform → cloud/modal_app.py. The images, the GPU, the storage and the server are defined in one Python file.
  • Stopping the instance → scaling to zero. 15 minutes after the last request, nothing is billed.
  • New: the trainer resumes after a preemption, and the proxy retries until a container is up.

What stays exactly as it is

  • Dataset v1, its card and the sign-off; the leak test on data/sft/ and configs/
  • train/sft.py's recipe, configs/sft_a.yaml, and the loss-mask check before step 1
  • The vllm serve flags the plan wrote for EC2: bf16, prefix caching, the hermes tool-call parser, LoRA rank 16
  • tau2-loop, its customer and its rules; score-pull, the sign test, MLflow and the viewer
  • The rule: one measured conversation or step before any paid batch

04 · the code

One new file and two small diffs, written to Modal's current docs but not yet run

These are proposals, not committed code. They follow Modal's guides as of today: @app.server for vLLM (the current example), Volumes, retries for preemption, and proxy tokens. The trainer's diff is the only change to train/sft.py.

src/tau_telecom_sft/cloud/modal_app.py new · proposed

The whole Modal side: two images, three Volumes, the training function and the server. The vllm serve flags are the ones the plan wrote for EC2's docker run. One extra check: the job refuses to start unless its copy of train.jsonl is the card's.

src/tau_telecom_sft/serve/proxy.py lines 62–87 · proposed diff

Two changes. The proxy sends the token headers it's given (from ~/.env; Servers require a token by default). And it waits out a 503, 429 or 502 instead of ending a conversation over a container that hadn't started. Each line in served.jsonl gains a retries count.

src/tau_telecom_sft/train/sft.py train() · proposed diff

Resume after preemption. The caller passes the run id, so Modal's restart of the same input finds the same folder, and TRL resumes from the newest checkpoint. callbacks.py also drops metrics.jsonl lines past that checkpoint's step, so the curve doesn't show steps twice.

Makefile new targets · proposed

Five targets. Only modal-train, and the Student's first request after modal-serve, start a GPU.

Also small: cli.py gains serve --remote, new-run-id and the Volume source for sync-runs. config.py reads the two proxy-token variables, and the run's instance becomes "Modal L4". docs/run_folders.md gains retries and resumed_from. Tests cover the retry, the token headers and the resume.

05 · how you'd see fine-tuning performance

The same three questions as s01, and on Modal the first one can be answered live

The viewer and MLflow read the run folder, which sync-runs brings home. Modal adds a live view while a container runs.

Is the training working?

  • Live: modal app logs -f shows each logged step as the trainer prints it.
  • Live: Modal's dashboard shows the container's GPU utilisation and memory.
  • Under a minute behind: make sync-runs WATCH=60 brings metrics.jsonl home. /train/:run and MLflow's tau-telecom-sft/train then draw the loss, learning rate and gradient norm, as they did for the smoke run.

What is it costing?

  • The Starter plan has no per-app cost report; that's Team and up. So run.json's cost_usd is seconds × list price (GPU + cores + GiB), labelled an estimate.
  • The workspace's spend counts against the $30 credit. A workspace budget can cap it.

Did it get better?

  • /eval/:run?vs=<R0>, unchanged: pass^1 to pass^4, fixed / broke / same by task, and the sign test's p.
  • Each served line's retries shows whether a preemption touched a conversation.
