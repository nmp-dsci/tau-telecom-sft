01 · the goal

M4 turns M3's baseline into a trained adapter, which M5 serves under one new name

The plan's M4 is one training run: configs/sft_a.yaml on 518 conversations covering all 74 training tasks, for a fixed 3 epochs, where the final checkpoint is the model. Here is what exists now and what M4 has to leave behind.

74 tasks, 518 conversations, 4 to 8 per task. They come from tau2's public board, where two open-weights agents, GLM-5 and Qwen3.5-397B, each ran every telecom task 4 times. That gives at most 8 per task, and 592 on the training tasks.
  • M1's filters kept 518 of the 592. 48 failed the task, and 26 failed a later rule: a broken ending, a bad tool call, a tool error, too long, or the fourth copy of the same tool calls.
  • Per task: 30 tasks keep all 8, 24 keep 7, 13 keep 6, 4 keep 5 and 3 keep 4. GLM-5 wrote 245 and Qwen3.5 273.
  • Per epoch, every conversation is trained on once, in 33 steps of 16, and the last step has 6. Three epochs make 1,554 passes in 99 steps.

Now, after M3

  • R0: the untrained 4B passes 6/40 test tasks and 8/74 training tasks at 1 trial (s03). Claude v2 passes 24/40.
  • The trainer works: at M2 it trained a 0.6B on 16 rows on the Mac. Loss fell from 1.47 to 0.87, and the mask check trained 11 of 11 agent turns and nothing else.
  • configs/sft_a.yaml was written at M2 for this run and hasn't been run yet.
  • The Student on Modal serves the base model, and its ADAPTERS is still {}. The runs Volume (Modal's persistent storage) has no adapter for it yet.
  • Not built yet: the Modal trainer, make modal-data, make modal-train and make sync-runs. s02 planned them, and M3 didn't need them.

After M4, the done-when

  • The final adapter is in runs/<id>/adapter/ on the runs Volume and on the Mac, with matching sha256. On Modal, that Volume takes the place of the plan's S3.
  • run.json records the config, the data hash 75718a64…, the commit, and Modal's image id in place of the plan's image tag. It also has the package versions and the cost.
  • MLflow tau-telecom-sft/train has every step: loss, gradient norm, learning rate, tokens a second and memory.
  • The checkpoints at the end of epochs 1 and 2 stay on the Volume for the record. They aren't the model.
  • The README's M4 row is filled in and the plan's M4 box is ticked, with the run id, steps, final loss, hours and the bill.
Fixed before the run starts. The plan says to fix the success criteria and the epoch count before M4 runs.
  • The epoch count is fixed at 3 by D1: every training task is trained on, so there's no held-out set to choose an epoch with.
  • The success criteria need restating. They were written for 4 trials (pass^3 ≥ 50% for the 4B), and since your call on 20 Oct both splits run at 1 trial. Question 1 in §10 asks how to restate them.

Liger is no longer what makes 24K tokens fit, so it's dropped.
  • What §7 assumed. The output layer was the problem: about 15 GB of fp32 scores at 24K tokens × 151,936 words. Liger's fused loss would never build that tensor.
  • What the code does. TRL 1.16, the version in uv.lock, already avoids it. Its SFTTrainer adds a fused LM head that projects only the positions that carry loss, in tiles, and never builds the logits (sft_trainer.py:1141–1147, utils.py:1548).
  • What the Liger flag does now. TRL 1.16 marks use_liger_kernel as deprecated, and it would only swap in Liger's layer kernels.
  • What dropping it gains. One CUDA-only dependency leaves the image, and with it one more thing that could break.

It also explains why M2 fitted on the Mac without Liger.

03 · architecture

The job runs on Modal and its folder comes home, because nothing on Modal can reach your MLflow

M4's picture. Accent outlines are new in M4; the dashed Student is M5's. The numbered edges are listed below the figure in the order they happen. The Mac drives everything with three make targets, and the GPU only runs while the job does.

  1. Leak check, then read v1. make modal-data runs make leak-check first, because the data Volume becomes something the trainer reads (rule 1).
  2. Upload, once. train.jsonl and stats.json go to the new -data Volume. raw/ never leaves the Mac.
  3. Start the job, detached. The Mac mints the run id, so a retried job writes the same folder. modal run --detach keeps it going if the Mac sleeps.
  4. Check the data. The job hashes its copy of v1 and stops unless the hash is the card's 75718a64….
  5. Load the weights. They come from the hf Volume M3 filled, at snapshot cdbee75, with no second download.
  6. Train and save. The job writes checkpoints every 11 steps and, at the end, the adapter. Volume writes are committed in the background every few seconds.
  7. Read the folder. sync-runs reads the run folder through Modal's Volume API. It skips the checkpoints.
  8. Bring it home. The folder lands in runs/<train>/, and the adapter's sha256 has to match the job's.
  9. Log to MLflow. The run, each new step, and at the end its files and the adapter go to the central MLflow. Only the Mac can reach it.
  10. See it in the viewer. /train/<run> draws the curve from the folder, as it did for M2.
  11. Serve it at M5. The Student reads /runs/<run>/adapter from the same Volume, so nothing is copied back.

07 · watching it train

Three questions while it runs, and what would make me stop it

Is it running?

  • modal run prints the job's own app id. Then uv run modal app logs -f <id> streams the trainer's lines.
  • Modal's dashboard shows the container's GPU use and memory.
  • make modal-stop stops the deployed Student, not this job. To stop the job, use uv run modal app stop <id>.

Is it learning?

  • make sync-runs RUN=<id> WATCH=60 brings metrics.jsonl home every minute.
  • The viewer's /train/<run> and MLflow's tau-telecom-sft/train then draw the loss, gradient norm, learning rate and tokens a second, less than a minute behind.
  • Expect the loss to fall through epoch 1 and step down at each epoch's start, because the model has seen those conversations before. With 3 epochs and no held-out tasks that's expected (D1), and M5's test score judges it.

What it costs

  • When the job ends, run.json holds cost_usd: list price × the attempt's wall time, labelled an estimate.
  • The bill itself arrives a day later: uv run modal billing report --start 2026-10-21 -r h --show-resources --json.
  • Modal keeps logs for only 1 day on the Starter plan, so the run folder is the record.
I'd stop the run and come back to you if any of these happens:
  • the loss is NaN, or rises for 10 steps in a row;
  • the gradient norm jumps by more than 10× its running level;
  • tokens a second fall below 60% of the measured step's;
  • memory climbs past 22 GB;
  • a third preemption happens, since the job allows 3 retries.

Stopping keeps every checkpoint, so the run can resume rather than start over.

08 · time and money

About $3.35–4.65 for all of M4, which would bring October's Modal spend to about $8 of the $30 credit

The throughput is my estimate, and the measured step replaces it before the full run starts. Each token costs about 33 GFLOP:

  • about 21.6 GFLOP is the 3.6B non-embedding weights, at 6 FLOP per weight once gradient checkpointing's recompute is counted;
  • about 12 GFLOP is attention over a 10,000-token conversation.

The L4 peaks at 121 TFLOPS in bf16. At 30–40% of that, it runs 1,100–1,500 tokens a second; plan §7 assumed 1,500. Modal's list prices from s02 add up to $0.80 (GPU) + 4 × $0.047 (cores) + 16 × $0.008 (GiB) = $1.12 an hour.
